# 獵豹玩中學：互動單元製作規範

使用者（獵豹數學）的**硬性要求**。每一條都來自實際被糾正過的錯誤，不可省略。做完任何單元，必須逐條對照「完成前檢查清單」。

## 零、三條最高原則（每次都要遵守）

1. **觀念優先：不是為了操作而操作。** 做操作，是因為藉由操作，能把一個**困難的基本觀念一下子弄懂**。
   - 規劃任何單元或關卡前，先用一句話寫出：**學生原本哪裡會卡（迷思）？操作怎麼讓他一下懂？** 寫不出來，就不要做這個操作。
   - 不為了「有互動」而加拖曳、滑桿、動畫；只能「按下一步看動畫」、沒有帶出觀念的內容，一律淘汰。
   - 每個關卡只教一個觀念；操作的結果要讓學生自己看見規則，不必背口訣。
2. **正確性第一。** 畫面上的每個數字、角度、圖形、公式，都必須用**獨立方法重算驗證**（見第六節）。寧可少做一個單元，也不能上線有錯的內容。
   - 企劃書、完成頁、進階卡裡的數值範例也要先手算或用程式核對。
   - 沒有查證的事不寫成事實（例如班級堂次、「別堂沒教」）；回報時誠實說明沒驗證到的範圍。
3. **畫面清楚：標好可動的點，文字與圖不互相遮蓋。**
   - **題目或說明中說「移動 H 點」，畫面上那個可拖動的點旁邊就要標出 `H`。** 凡是可拖動、題目會提到的點，一律標字母，不可只畫一個沒有名字的圓點。
   - **文字不蓋圖、圖（線、點、把手）也不蓋文字。** 標籤、度數、讀數、字母之間也不可互相重疊。

## 一、設計原則（最重要）

1. **操作為主，答案要在操作中發現**
   - 不要把小測驗做成「填空（numBox）」或「選擇題」。使用者明確說過：題目大多是填空、不能操作，要改。
   - 好的關卡長這樣：**拖曳把手找出符合條件的位置**、滑桿、步進器調數值達到目標、倒水、疊切片、把圖形拖到定位、龜步走回起點、格線上找滿足條件的點。答案由畫面上的即時讀數「看出來」，不是打字輸入。
   - **預測題**（`P.choice` 且 `predict: true`，「先猜猜看」）可以保留，因為後面一定接著操作，用來對照「猜的」和「看到的」。
   - 目標導向：給一個目標（「讓 ∠APB＝35°」「體積剛好是 24，找 3 種疊法」），讓學生自己操作到達成。多目標用依序出現的子目標（目標 1/3…）。
   - 提示文字**不要直接洩漏答案**（寫「想想哪兩個平方數加起來是 13」，不寫「用橫 2、直 3」）。
2. **單元結構**：預測＋操作 → 再一個操作 → 換個外觀／推廣 → 3～4 個操作關卡（`P.taskSeq`）→ 完成頁（`P.complete`）。一個單元 4～6 步，8 分鐘左右。
3. **答對後不能自動跳題**：一律出現「下一題 ▶」按鈕，使用者手動按（核心 `Play.later()` 已統一處理；多關用 `P.taskSeq`，不要自己 `setTimeout` 換題）。最後一關完成後也是手動按「繼續」。
4. **每一步都要能「看詳解」過關**：探索步驟必寫 `api.solve(fn)`（fn 要把畫面操作到完成）；`P.taskSeq` 的每一關用 `setSolve(fn)`。把手用 `handle.moveTo(點)`、滑桿設 `.value` 再呼叫繪圖函式。
   - **看詳解的綠框，開頭一定要明確寫「正確答案是：…」**（使用者明確要求）。學生按「看詳解」不應該還要回頭看圖、慢慢讀說明去推敲答案。
     - 預測題／選擇題：每個選項都要標好哪個是對的（預測題也要）：`options: [{ t: '…' }, { ok: true, t: '…' }, …]`。看詳解會自動寫「正確答案是：<選項>」，不可再用「先跳過預測」。
     - 操作關卡：`setSolve(fn, '答案文字')`（探索步驟用 `api.solve(fn, hold, '答案文字')`），核心會把「正確答案是：…」放在最新出現的綠框（規則框）**最前面**；沒有綠框就自己放一個。多個答案要全部寫出（例如「x＝−1 和 x＝5」），不要只靠提示訊息。
     - 沒傳答案文字時，核心會拿示範過程中最後一則 `P.toast` 當答案；所以 toast 要寫成完整、明確的答案（例如「解：x ＜ 4」），不要寫「找到了」「答對了」。
     - 新增或修改單元後，要跑「看詳解稽核」：逐步逐關按看詳解，確認每一次之後都出現「正確答案是：」。
5. **預測題之後的操作要擋住**：預測前操作元件顯示「先做上面的預測」並復原。

6. **拖到答案位置要有明顯回饋**（使用者要求）：把手拖到正確位置時，那個位置要留下**綠圈＋勾勾**，不能只靠下方小字。核心已自動處理：在把手的 `onMove` 裡呼叫 `P.toast(...)`、`done()`（taskSeq）、或讓某個 `.pl-pill` 變成 `is-ok`，就會在該位置標記；「找 N 個」類的關卡每找到一個要再呼叫 `board.goalMark(位置)` 讓它留著。讀數膠囊（pill）與「目標 n / N」徽章已放大，答對的膠囊是實心綠色。

7. **規則由畫面自己寫出來。** 學生操作後，規則框（`P.ruleBox`）自動顯示發現的規則；學生不必填字。符號、正負、範圍等用顏色直接表示（例如內積正綠、零灰、負紅；方程式的解集合在數線上塗色）。
8. **兩種算法並列驗證。** 公式有兩種寫法時（如 |a||b|cos θ 與 x₁x₂＋y₁y₂），畫面並列顯示兩個數值，讓學生看到它們永遠相等，而不是兩個要背的公式。
9. **3D 單元的手勢。** 可旋轉的視角放在背景手勢；**拖動點的優先權高於旋轉**，拖點時視角不可轉動。平面用半透明，點不可被平面遮住。必須在手機 375px 實測確認。
10. **規劃單元時先去重。** 先看 `assets/play/lessons/` 與 `meta_*.py`、`build_pages.py`，確認網站是否已有同主題；有重疊就決定「新增」或「擴充」，並重用現有元件，不另寫一份。
11. **內容大就拆。** 一個主題太大時拆成 Part 1／Part 2 或分階段，每個 Part 單獨成立、約 4～6 步、8 分鐘；重複出現的關卡（如二面角）只做一次完整版，其他單元沿用同一個元件。

## 二、角度與數字顯示（常被糾正）

- **可拖動的點旁邊標出字母**（如 H、D、P）。題目說要移動哪一個點，畫面上就要看得到那個點的名字；多個可動點要各自標，字母不可被線或把手蓋住。
- **文字與圖不可互相遮蓋**：字母、度數、讀數不壓在線與把手上，線與把手也不蓋住文字；標了字母的點旁要留出位置。
- **90° 一律畫直角符號**（小方框），不是圓弧。用 `PlayGeo.wedge`（自動處理）；格線上的直角用 `board.rightMark`。
- **每個角旁邊都要標出度數數字**，拖動／操作時**即時更新**；不可只放在下方 pill，也不可只寫符號 x（要寫「x＝35°」）。
- 多個角加起來要剛好等於總和（外角和 360°、三角形 180°…）：整數化用「最大餘數法」，不要各自四捨五入。
- 數字要**正確**：用獨立公式重算驗證（見下方驗證）。凸多邊形等要用 `PlayGeo.polyAngles`（會拒絕頂點重疊、凹多邊形、自己交叉的星形），**不要自己湊總和**。
- 文字不能被把手、端點或別的文字蓋住：核心 `Board` 已內建 `declutter`（MutationObserver 自動挪位），新單元不必自己算標籤位置；但要把可拖動的限制在畫面中間範圍，留空間給標籤。

## 三、手機優先

- 每個單元都要在 **375px 寬**驗證：無橫向捲動、畫布寬度合適、文字不被切。
- 觸控把手範圍由核心處理（≥24px）；操作元件用 `P.stepper`／`P.slider`（已適配手機）。

## 五、製作流程（檔案與工具）

1. `assets/play/lessons/<slug>.js`：`new P.Lesson({id,title,steps})`；每步 `function(st, api)`。
   - 常用：`P.Board`（格線畫板）＋`board.handle({pos,candidates,valid,onMove})`、`P.slider`、`P.stepper(label,min,max,value,onChange,fmt)`、`P.choice`（只用於預測）、`P.pill`、`P.ruleBox`、`P.hint`、`P.instr`、`P.taskSeq`、`P.complete`。
   - 共用幾何：`assets/play/play-geo.js`（`PlayGeo`）；用到的單元在 meta 的 `libs` 加 `'assets/play/play-geo.js'`。立體單元用 `PS.scene`、`PS.cubeFaces`。
   - 事件追蹤：`P.track('aha', {id, step})`、完成時 `P.track('transfer_ok', {id})`。
2. 中繼資料：`assets/play/meta_*.py` 的 `ENTRIES`（slug／title／grade／area／mins／blurb／see／deep／classes／desc／art 縮圖 SVG 320×130）。平面幾何放 `meta_geometry.py`、立體放 `meta_solid.py`。
3. `python assets/play/build_pages.py` 產生頁面與 `play.html`。**坑**：它會把舊的 `play-*.html` 改成 LF，要 `git checkout` 還原舊頁，只保留 `play.html` 與新頁。
4. `sitemap.xml` 手動補 `<url>`（檔案是 CRLF，別整個重跑 `npm run seo`）。
5. 完成頁要有：發現（aha）、性質卡、深度標尺、進階卡（teasers，含真實班級堂次）、家長區、`classes`。

## 六、驗證（做完必做，使用者強調「正確性相當重要」）

詳細腳本在 `scripts/qa-harness.js`（用法見該檔開頭）。

1. **走完整個單元**：用「看詳解」＋「下一題」逐步走到完成頁，檢查 console 錯誤。
2. **隨機拖曳壓力測試**：對每個有把手的步驟／關卡做大量隨機拖曳（真實 pointer 事件），每次檢查：
   - 畫面數字加總正確；
   - 由頂點／座標**用獨立公式重算**（例如 `atan2(cross, dot)`）並和畫面標籤逐一比對；
   - 沒有文字壓到 `.pl-hd` 把手或其他文字、沒跑出畫布；
   - 手機 375px 再跑一次。
3. **真實完成動作**（不是看詳解）：確認答對後停在原題、出現「下一題」。
4. 新增或修改核心（`play-core.js`）後，用舊單元（如角平分線）做回歸測試。

### 測試陷阱
- 瀏覽器會用**快取的舊 JS**：測試前對改過的檔案 `fetch(url,{cache:'reload'})` 再重新載入；必要時換主機名稱（localhost／127.0.0.1）。
- 用 Python 腳本修補 JS，替換範圍沒算好會留下**同名函式重複定義**，後者覆蓋前者（曾讓舊演算法一直在跑）。修補後掃描頂層 `function` 名稱是否重複。
- 把手有彈簧動畫，檢查前要等約 450ms。
- 折線 `h('polyline')` 一開始 points 為空會被 `degen()` 永久隱藏，更新 points 後要 `style.display=''`。
- 單次瀏覽器腳本超過約 45 秒會逾時：用「不 await 的非同步迴圈＋把結果寫到 window」再輪詢。
- 截圖可能落後一拍，需要再截一次。
- 手機（375）與桌機（約 1000）**兩種寬度都要跑壓力測試**：`pl-svg--sm` 的小畫板在桌機太窄，刻度數字會互壓；座標平面一律不要用 `sm`。
- 標籤避讓的尺寸要用「文字 bbox」：單一字母約半寬 0.3、半高 0.45（畫板單位），可動把手的障礙框是 ±0.62；重疊時 `PV.gap` 回傳負數，挑位置時才分得出哪個比較不糟。候選位置要多給幾圈半徑，標籤太近或太擠才有地方去。
- 標籤放在「基線 − 0.27」，文字框的中心才會落在你算的位置（`PV.pick`、`PV.place` 已處理）。

## 七、版本與上線

- **每次做完單元的最後一步一定是「更新到主資料夾」**（使用者明確要求）：commit 後到主資料夾 `E:\20260323_LiyunWG_Cheetah_website` 執行 `git merge --ff-only <分支>`，再告訴使用者已更新；不可只留在 worktree。
- 修改後**要直接在主資料夾生效**（使用者從主資料夾的 `index.html`／`play.html` 用 `file://` 檢查）：在 worktree 改完 commit 後，到主資料夾 `git merge --ff-only <分支>`（主資料夾有未 commit 的修改時先問）。
